Ты — ведущий разработчик и технический архитектор. Разработай полноценную self-hosted платформу управления проектами и разработкой для нашей команды.

Нужен работающий продукт, который ты самостоятельно реализуешь, запустишь в доступном облачном окружении, проверишь и отправишь в подключённый GitHub-репозиторий. Не ограничивайся архитектурой, прототипом интерфейса или генерацией файлов.

## 1. Контекст и цель

Нас пятеро: руководитель разработки и четыре специалиста — backend, frontend, mobile и DevOps.

Нужна собственная бесплатная система, объединяющая возможности управления проектами из OpenProject Enterprise, Jira, YouTrack, Azure Boards и Taiga:

- задачи, канбан, бэклог и спринты;
- дорожные карты, диаграмма Ганта и зависимости;
- документация и база знаний;
- учёт времени, загрузки и бюджета;
- отчёты и аналитика;
- автоматизация процессов;
- интеграции с инструментами разработки;
- управление доступом, двухфакторная аутентификация и аудит.

Реализуй эти возможности самостоятельно, используя подходящие открытые библиотеки. Не копируй закрытый код и не обходи лицензирование чужих продуктов. Не создавай искусственных ограничений пользователей, проектов, функций или истории.

Основная обязательная интеграция — **наш self-hosted GitLab Community Edition**. Приложение не должно требовать GitLab Premium/Ultimate.

GitHub используется для хранения исходного кода создаваемого приложения. GitLab CE — отдельная интеграция внутри продукта. Не путай эти назначения.

## 2. Организация разработки: Superpowers и субагенты

Используй Superpowers из официального проекта:
https://github.com/obra/superpowers

Сначала проверь, доступен ли он в окружении. Если отсутствует, попробуй установить по актуальной официальной инструкции для Codex в пределах разрешённых возможностей.

Применяй соответствующие доступные навыки для:
- проработки требований и архитектуры;
- составления плана;
- разработки через субагентов;
- тестирования;
- систематической отладки;
- проверки результата перед завершением;
- ревью и завершения ветки.

Используй настоящие инструменты субагентов, если они доступны. Распределяй независимые задачи между агентами с чёткими границами файлов и ответственности. Возможные направления: backend, frontend, GitLab, безопасность, тестирование и инфраструктура.

Согласуй общие модели данных и API до параллельной реализации. Изолируй конфликтующие изменения через ветки/worktrees. Выполняй независимое ревью требований и качества кода, где позволяет среда.

Если Superpowers или субагенты технически недоступны, честно зафиксируй ограничение и продолжай доступным способом. Не изображай мультиагентную работу текстовыми ролями.

Не останавливайся после каждого этапа за подтверждением. Самостоятельно принимай обратимые инженерные решения и записывай существенные допущения. Спрашивай только при блокирующей неопределённости, отсутствии необходимых доступов или риске необратимого изменения существующих данных.

## 3. Проверка окружения и репозитория

До разработки:

1. Найди подключённый GitHub-репозиторий. По моим данным, подключён один; проверь это.
2. Прочитай README, AGENTS.md и существующий код. Сохрани полезную структуру и чужие изменения.
3. Проверь доступные runtime, сеть, терминал, браузер, Docker, базы данных и возможность запуска фоновых процессов.
4. Проверь возможность получения зависимостей и отправки коммитов.
5. Создай рабочую ветку, не используй force-push.

Если выбор репозитория неоднозначен, запроси уточнение. Не создавай новый удалённый репозиторий и не меняй видимость существующего.

Под «запустить в облаке» я имею в виду реально запустить frontend, backend, БД и фоновые задачи в твоём доступном вычислительном окружении и проверить приложение через HTTP и браузер. Постоянный публичный хостинг не требуется.

Если Docker недоступен, попробуй запустить необходимые процессы непосредственно. Если возможности среды не позволяют запуск, сообщи точное ограничение; не утверждай, что приложение запущено или проверено.

## 4. Архитектура и развёртывание

Проектируй для пяти активных пользователей с возможностью роста до нескольких десятков.

Предпочтительна архитектура модульного монолита. Не создавай микросервисы и Kubernetes без доказанной необходимости.

Если репозиторий пустой, используй:
- TypeScript;
- React для интерфейса;
- NestJS для API и фоновых процессов;
- PostgreSQL;
- Redis и очередь заданий при необходимости;
- совместимый с S3 файловый storage и вариант хранения на локальном диске;
- Docker Compose для установки.

Допускается другой стек, если он лучше соответствует существующему репозиторию; объясни выбор.

Предусмотри:
- версионируемый REST API и OpenAPI;
- миграции БД;
- транзакции, индексы, пагинацию;
- фоновые задания с повторными попытками;
- обновления интерфейса без перезагрузки там, где они нужны;
- health/readiness endpoints;
- структурированные логи без секретов;
- конфигурацию через environment variables;
- отсутствие обязательных внешних SaaS.

Рабочий ориентир — сервер с 4 CPU и 8 ГБ RAM. Измерь потребление на доступной машине и укажи условия измерения.

Подготовь production Docker Compose, постоянные volumes, HTTPS через reverse proxy, инструкции обновления, резервного копирования и восстановления. Не публикуй БД и Redis наружу по умолчанию.

## 5. Пользователи и безопасность

Реализуй:

- первичную настройку владельца без стандартного публичного пароля;
- вход по email/паролю, приглашения, выход и восстановление пароля;
- отключённую по умолчанию свободную регистрацию;
- безопасное хеширование паролей Argon2id;
- управление сессиями, устройствами и отзывом доступа;
- TOTP 2FA с QR-кодом;
- одноразовые резервные коды, хранимые в виде хешей;
- обязательную 2FA по политике организации;
- WebAuthn/passkeys как дополнительный способ входа;
- безопасное подключение, отключение и восстановление факторов;
- защиту от повторного использования TOTP и перебора;
- SSO через OIDC и подключение LDAP/AD.

Внешние способы входа не должны позволять обходить установленную политику MFA. Опиши правила доверия к внешнему провайдеру.

Роли: владелец, администратор, руководитель проекта, участник, наблюдатель, внешний гость. Добавь настраиваемые роли и разрешения на уровне проектов.

Проверяй права на сервере для каждого объекта, включая поиск, экспорт, вложения, уведомления и realtime-каналы. Скрытая кнопка не является защитой.

Предусмотри CSRF, XSS, SQL injection, IDOR, SSRF, rate limiting, безопасные cookies, ограничение загрузок, проверку MIME и безопасную выдачу файлов.

Токены интеграций и TOTP-секреты шифруй с ключом вне базы данных. Не возвращай сохранённые секреты клиенту и не записывай их в логи. API-токены приложения должны иметь scopes, срок действия и отзыв.

Для интеграций с офисными сервисами разрешай явно настроенные внутренние адреса. Защита SSRF должна блокировать metadata endpoints, опасные redirects и произвольное сканирование сети, сохраняя возможность подключения внутреннего GitLab.

Веди журнал значимых административных действий, изменений прав и событий аутентификации. Не заявляй его криптографическую неизменяемость без соответствующей реализации.

## 6. Проекты, задачи и рабочие процессы

Реализуй:
- организацию, команды, проекты, подпроекты и портфели;
- шаблоны проектов и задач;
- типы: epic, feature, story, task, bug, subtask;
- стабильные ключи задач, например ATR-123;
- описания с Markdown, комментарии, упоминания, реакции и вложения;
- исполнителя, автора, наблюдателей, приоритет, метки, компоненты, версии и сроки;
- оценки времени и story points;
- типизированные пользовательские поля;
- иерархию, связи, блокировки и зависимости;
- историю изменений, массовые операции и повторяющиеся задачи;
- архивирование, корзину и контролируемое восстановление;
- полнотекстовый поиск и сохранённые фильтры.

Рабочие процессы должны настраиваться: статусы, разрешённые переходы, роли, обязательные поля и проверки переходов.

Предустановленный процесс:
«Бэклог → Готово к работе → В работе → Проверка → Готово».
Из «Проверки» можно вернуть задачу в «Вернул в работу».

Добавь настраиваемое правило: если у исполнителя есть возвращённые задачи, начало новых задач блокируется либо требует разрешения руководителя.

Представления:
- таблица с настройкой столбцов;
- канбан с drag-and-drop, swimlanes и WIP-лимитами;
- календарь;
- roadmap;
- диаграмма Ганта с зависимостями, вехами, рабочими днями и базовым планом.

Перенос карточек и изменение сроков должны реально сохраняться и соблюдать права и workflow.

## 7. Спринты и аналитика

Поддержи бэклог, планирование, запуск и завершение спринта, распределение capacity, оценки, перенос незавершённых задач и несколько команд.

Предустановка: двухнедельный спринт; первая неделя — разработка, вторая — исправления и подготовка релиза. Расписание и процесс настраиваются.

Отчёты:
- burndown и burnup;
- velocity;
- planned/completed scope;
- изменения объёма спринта;
- predictability;
- lead time и cycle time;
- cumulative flow;
- throughput;
- aging незавершённых задач;
- возвраты с проверки и rework;
- план/факт времени и загрузки.

Критически важно: перенос задач между спринтами не должен переписывать историю. Фиксируй исходный состав спринта и события изменения scope. Разделяй завершение, удаление из спринта, перенос и возврат в работу.

Для каждой метрики определи формулу, источник данных и поведение на пограничных случаях. Не создавай произвольные «индексы здоровья» без прозрачной методики.

Добавь персональные и командные дашборды, фильтры по проекту/периоду/исполнителю и экспорт CSV/PDF.

## 9. GitLab CE — обязательная глубокая интеграция

Используй официальные API и возможности Community Edition. Проверь документацию и совместимость с поддерживаемыми версиями. Укажи проверенный диапазон версий.

Реализуй:
1. Подключение собственного GitLab по URL через подходящий токен или OAuth.
2. Проверку соединения, разрешений и доступных проектов.
3. Несколько подключений и привязку нескольких репозиториев к проекту.
4. Связь задач с branches, commits, merge requests, issues, pipelines и releases.
5. Распознавание ключей задач в названиях веток, сообщениях коммитов и MR.
6. Панель разработки в задаче: MR, состояние ревью, pipeline и ссылки в GitLab.
7. Создание ветки из задачи с настраиваемым шаблоном имени.
8. Создание GitLab issue и настраиваемую двустороннюю синхронизацию выбранных полей.
9. Сопоставление пользователей, labels и milestones.
10. Настраиваемые переходы задач по событиям GitLab.
11. Приём project webhooks для необходимых событий.
12. Фоновую сверку данных через API после пропущенных событий.
13. Страницу диагностики, ошибок, повторной синхронизации и состояния подключения.

Не предполагай наличие платных approvals, group webhooks, epics или других функций GitLab. Если возможность зависит от редакции/версии, обнаруживай её и показывай понятное состояние.

Проверяй подлинность webhook способом, поддерживаемым соответствующей версией GitLab. Обеспечь дедупликацию, идемпотентность, обработку событий не по порядку, повторные попытки и защиту от циклов синхронизации.

Определи источник истины для каждого синхронизируемого поля и разрешение конфликтов. Потеря доступа к GitLab не должна удалять локальные задачи.

Учитывай pagination, rate limits, истечение токенов, недоступность сервера и изменение имён проектов.

Не раскрывай приватные данные репозиториев участникам приложения только потому, что сервисный токен имеет широкий доступ. Определи правила видимости и отдельно протестируй их.

Автоматическое создание webhooks должно быть отдельным явным действием администратора. Не изменяй реальные репозитории и настройки GitLab при обычной проверке соединения.

## 10. Остальные интеграции и автоматизация

Предусмотри расширяемый интерфейс коннекторов. В рамках этого ТЗ реализуй:
- SMTP: приглашения, восстановление доступа, уведомления и дайджесты;
- GitHub: связь задач с commits, PR и статусами проверок;
- Telegram и Slack: настраиваемые исходящие уведомления;
- OIDC и LDAP/AD;
- S3-совместимое хранилище;
- WebDAV/Nextcloud для привязки файлов;
- календарную подписку iCalendar;
- импорт/экспорт CSV и JSON;
- импорт задач из GitLab;
- документированный REST API;
- исходящие webhooks с подписью, retries и журналом доставок.

Это конечный обязательный перечень, а не обещание поддержки любого существующего сервиса.

Добавь движок «событие → условия → действия»: назначение, изменение полей, уведомления, создание задач и HTTP webhooks. Нужны журнал выполнения, защита от циклов и безопасное тестирование правила без внешних действий.

Без внешних credentials коннекторы должны оставаться явно ненастроенными. Не подменяй реальные интеграции демонстрационными ответами.

Каждая отображаемая функция должна работать. Не оставляй фиктивные кнопки и захардкоженные показатели в рабочих разделах.

## 12. Тестирование и фактический запуск

Пиши тесты в разумных пределах: проверяй риски и поведение, а не формальное покрытие каждой строки.

Обязательно:
- unit-тесты вычислений, workflow, прав и конфликтов синхронизации;
- integration-тесты API с настоящей PostgreSQL;
- тесты фоновых заданий, миграций и идемпотентности;
- Playwright E2E основных пользовательских сценариев;
- тесты безопасности авторизации и MFA;
- проверки сборки, типов и lint;
- проверка зависимостей и случайно закоммиченных секретов.

Ключевые E2E:
1. Первичная настройка → вход → подключение TOTP → выход → вход с 2FA.
2. Использование recovery code и запрет его повторного использования.
3. Приглашение участника и проверка ограниченных прав.
4. Создание проекта, задачи, спринта и работа с доской.
5. Возврат задачи с проверки и применение правила процесса.
6. Закрытие спринта с переносом задач без искажения истории.
7. GitLab webhook → обновление MR/pipeline → применение правила.
8. Повтор webhook без дублирования и повторного действия.
9. Недоступный GitLab → retry → восстановление синхронизации.
10. Загрузка файла, поиск и экспорт с проверкой доступа.
11. Резервное копирование и восстановление в чистой среде.

Для интеграций используй контрактные тесты, реалистичные fixtures и тестовые серверы. Отдельно указывай, что проверено на mock, а что на реальном сервисе.

По возможности подними временный GitLab CE для сквозной проверки. Если ресурсов или доступов недостаточно, не заявляй проверку на живом GitLab.

Реально открой приложение в браузере и проверь основные экраны. Сохрани скриншоты и результаты. Измерь основные операции при пяти одновременных пользователях и исправь обнаруженные узкие места.

Не объявляй успех по одному факту успешной сборки. Не отключай тесты и защитные проверки ради зелёного результата.

- способ проверки;
- фактический статус и ограничение, если оно есть.

Реализуй последовательно:
1. Инфраструктуру, аутентификацию, MFA и доступ.
2. Проекты, задачи, workflow, доски и спринты.
3. GitLab CE.
4. Аналитику и планирование.
5. Wiki, время, ресурсы и бюджеты.
6. Остальные интеграции и автоматизации.
7. Проверку безопасности, развёртывания, восстановления и UX.

Это порядок выполнения полного ТЗ, а не разрешение закончить после MVP.

Если работа не помещается в один сеанс, сохрани коммиты и точный checkpoint: завершённое, незавершённое, результаты тестов и следующий шаг. Не выдавай частичную реализацию за завершённый продукт.

## 14. Документация и доставка в GitHub

Подготовь:
- исходный код и lockfiles;
- Dockerfiles и production Docker Compose;
- `.env.example` без секретов;
- миграции и отдельные demo seeds;
- README с воспроизводимым запуском;
- инструкции по HTTPS, SMTP, GitLab CE, MFA и SSO;
- OpenAPI;
- инструкции резервного копирования, восстановления и обновления;
- описание метрик и модели доступа;
- CI через GitHub Actions;
- отчёт тестирования и известные ограничения;
- подходящую открытую лицензию и сведения о лицензиях зависимостей.

CI должен запускать доступные автоматические проверки, включая тесты с БД и сборку контейнеров. Изменения схемы должны иметь проверяемый путь обновления; для необратимых миграций опиши восстановление из резервной копии.

После реализации и проверок:
1. Проверь diff и отсутствие секретов, runtime-данных и ненужных артефактов.
2. Закоммить изменения осмысленными коммитами.
3. Отправь рабочую ветку в подключённый GitHub-репозиторий. Я прямо разрешаю этот push.
4. Создай PR, если это поддерживается доступными инструментами.
5. Не выполняй force-push, не сливай PR и не развёртывай приложение в нашей рабочей инфраструктуре без отдельной инструкции.
6. Проверь, что отправленный commit действительно доступен удалённо. Если CI доступен, проверь результат и исправь связанные с изменениями ошибки.

В финальном отчёте дай:
- ссылку на репозиторий, ветку, commit и PR;
- реализованные возможности;
- фактически выполненные проверки и их результаты;
- способ запуска;
- сведения о тестовом окружении;
- необходимые настройки реальных интеграций;
- все оставшиеся ограничения.

Если доступов к push нет, прямо сообщи это и сохрани готовые локальные коммиты. Не заявляй, что код отправлен.

Начни с проверки окружения и репозитория, затем составь план и приступай к реализации. Цель — проверенное, воспроизводимо запускаемое приложение с честной матрицей готовности.
