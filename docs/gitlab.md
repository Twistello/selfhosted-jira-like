# GitLab CE: настройка и границы реализации

Реализованы вызовы официального API v4: [branches](https://docs.gitlab.com/api/branches/), [issues](https://docs.gitlab.com/api/issues/), [project webhooks](https://docs.gitlab.com/api/project_webhooks/). Платные approvals, group hooks и GitLab epics не используются. Документация просмотрена 2026-11-18. **Подтверждённого диапазона версий GitLab нет:** проверка выполнялась на реалистичном локальном HTTP fixture и PostgreSQL, живой GitLab CE не запускался.

1. Добавьте точный origin собственного GitLab в `INTEGRATION_ALLOWED_ORIGINS`, например `https://gitlab.internal.example`. HTTP разрешается для явно настроенной внутренней тестовой установки, в рабочей сети используйте TLS. Metadata endpoints блокируются, redirects запрещены; DNS проверяется перед запросом, соединение закрепляется за проверенным IP. Произвольного сканирования сети нет.
2. Администратор создаёт подключение в интерфейсе с URL и Personal Access Token. Для чтения нужен подходящий доступ к API; создание branches/issues/hooks требует write API и соответствующей роли в репозитории. Минимальные scopes зависят от включённых действий, автоматического обнаружения granular scopes пока нет. Сохранённый токен никогда не возвращается клиенту.
3. Проверка соединения вызывает `/user`, список репозиториев использует membership и pagination. Связывание сохраняет числовой project ID, поэтому переименование пути не ломает адресацию.
4. По умолчанию видимость — только администраторы. Публикация данных участникам проекта — отдельный выбор администратора. Импорт issues в общие задачи требует разрешённой видимости проекта; confidential issues пропускаются. Отзыв публикации останавливает будущую синхронизацию, но уже явно импортированные данные задач остаются общими и автоматически не удаляются.
5. Создание webhook — отдельная кнопка с подтверждением. Callback строится из `PUBLIC_URL`. Принимается `X-Gitlab-Token`, хеш которого хранится в БД; delivery UUID обязателен для дедупликации. События записываются в durable очередь до ответа 202.

Подключения допускаются во множественном числе; одна запись связывает один удалённый репозиторий, несколько записей могут относиться к одному проекту приложения. Сервер принимает push/MR/pipeline/issue/release, распознаёт ключи задач, сохраняет development links, игнорирует более старый внешний timestamp, периодически сверяется через API. Повторы используют PK receipt и upsert ссылок. Jobs: SKIP LOCKED, backoff, максимум шесть попыток, возвращение просроченной lease в pending. Ограничение страниц одного запроса приводит к явной ошибке, а не тихой обрезке.

API-only операции: `POST /tasks/:id/branch`, `POST /integrations/:id/issues/import`, `POST /tasks/:id/gitlab-issue`, `GET /tasks/:id/development`. Пока отсутствует полноценная панель разработки в интерфейсе, создание нового GitLab issue из локальной задачи и mapping пользователей/milestones.

Inbound issue sync включается только явным импортом. Удалённые title/description/labels/due-date обновляют локальную задачу; status применяется через проверки workflow, конфликт сохраняется как `gitlab.sync_conflict`. Явная исходящая операция передаёт текущие локальные поля, затем нормализует ответ GitLab. Общей настраиваемой политики источника истины по каждому полю и полноценного разрешения одновременных двусторонних конфликтов ещё нет. Автоматического изменения workflow по произвольным MR/pipeline событиям нет. При отказе GitLab локальные задачи не удаляются.

GitHub в этом репозитории используется для хранения исходного кода. Интеграция продукта с GitHub commits/PR/checks пока не реализована.
